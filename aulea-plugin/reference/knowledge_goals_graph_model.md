# Knowledge goals graph model

The **model** is `design/knowledge_goals_graph.json` — the DESIGN SSOT store, sole writer
`curriculum-architect`, shape enforced by
`.claude/reference/knowledge_goals_graph.schema.json` (draft 2020-12; the schema is the
authority — this doc explains it, it doesn't replace it). Viewed and edited through
`tools/graph/` (see `tools/graph/README.md`); a git commit of the file *is* the certification —
there is no in-file status field.

A worked example: the file itself, `design/knowledge_goals_graph.json` — regenerated by
`curriculum-architect` against a real course's `specifications/`, not hand-authored.

---

## Top level

```json
{
  "course_name": "…",
  "personas": ["P-DEV", "P-OPS"],
  "nodes": [ … ],
  "edges": [ … ]
}
```

`personas` is a flat list of persona **ids** referenced elsewhere in this file (`audience`,
`held_by`, `skippable_by`, `persona_variant`) — not persona *definitions*. Names, cohort counts,
and everything else about a persona live in the STUDENT_PERSONAS SSOT
(`specifications/student_personas.md`), which this file doesn't reference. `nodes` sorted by `id`,
`edges` sorted by `(from, to)` — see "Formatting and diffability" below.

## Nodes

Three types, distinguished by `type` and an id prefix:

| `type` | id prefix | meaning |
|---|---|---|
| `Baseline` | `BSL-` | Knowledge the cohort already has coming in. Requires nothing (it's the substrate everything else is built on). |
| `Prerequisite` | `PRQ-` | A teachable concept the course must cover on the way to a `DesiredResult` — never a task or a tool ("understand how to deploy a route", not "run the deployment script"). |
| `DesiredResult` | `DR-` | A course objective — what the graph is decomposing backward from. |

Common fields on every node: `id`, `type`, `provenance_tags` (one or more of `stated` /
`inferred` / `inherited_inferred` / `invented_framing` / `risk` — confidence/provenance, not
decoration), `key` (short mnemonic the id is derived from), `description`, `knowledge_type`
(`declarative` / `procedural` / `contextual`).

Type-specific fields:
- `Baseline`: `held_by` (persona ids who already have it — a baseline held by only some personas
  is normal).
- `Prerequisite` / `DesiredResult`: `audience` — `"all"` or a non-empty persona-id array; who this
  node is for.
- `skippable_by` (either type with `audience`): persona ids inside `audience` who already hold the
  node and may skip it. Normal for it to be empty or omitted.
- `persona_variant`: optional, only when the same node is genuinely reached differently by
  different personas — one `{persona, variant}` entry per persona that differs.
- `Prerequisite` only: `root: true` for a *deliberate* root (no incoming edge, on purpose) —
  requires `root_rationale`, a one-line reason. A `Prerequisite` with no incoming edge and no
  `root: true` is a graph bug, not a valid state (see "Closure check" below).
- `depth_staging: {pass, depth, note}` — present only when this node is one pass among repeated
  visits to the same topic (spiralling, per Kolb's repetition-through-variation). `depth` is
  `shallow` or `deep`; each pass is its own node (`PRQ-<MNEMONIC>-SHALLOW` /
  `PRQ-<MNEMONIC>-DEEP`), connected in order — this field marks which pass a given node *is*, it
  does not itself connect the passes (an edge does that).

## Edges

```json
{ "from": "PRQ-CONTAINERIZE-GATEWAY", "to": "BSL-DOCKER", "reason": "…" }
```

`Requires`: `from` cannot be tackled before `to` is understood — `to` is the more foundational
node. `reason` is required and states *why*, not just that the edge exists. This is the only edge
type; there is no separate "Enables" relation (an earlier draft of the tooling used that name in
one place — corrected, see `.claude/agents/curriculum-architect.md`).

## Closure check

Every node needs a path down to substrate: an outgoing edge (it appears as `from` on some edge,
i.e. it requires something) — unless it's a `Baseline` (requires nothing, by definition) or a
`Prerequisite` marked `root: true` (deliberately requires nothing). A node failing this is a dead
end the graph forgot to connect downward. `tools/graph/check.mjs` (`tools/graph/graph check
<file>`) runs this mechanically, alongside schema validation — see its file comment for the
direction-of-the-edge note (the agent doc's prose describes this check in terms that read
naturally as the *opposite* direction; the check's actual direction was settled by round-tripping
the real, human-approved graph rather than the prose alone).

Not yet automated: *audience reachability* — if every incoming edge into a node bottoms out at a
`Baseline` some persona in the node's `audience` doesn't hold, that persona has no path in. The
agent is instructed to check this while building the graph; `check.mjs` doesn't (yet) verify it
independently.

## Formatting and diffability

The store is git-diffed, so a save must not reformat lines it didn't change. The convention
(reverse-engineered from the real file, encoded in `tools/graph/server/formatGraph.mjs`, and what
`curriculum-architect` is instructed to match by hand):
- An array of primitives renders inline: `["P-DEV", "P-OPS"]`.
- An array-item object with **3 or fewer keys, all leaf-valued** (primitive or array-of-primitives)
  compacts onto one line — edges (`{from, to, reason}`), `persona_variant` entries
  (`{persona, variant}`).
- Everything else — nodes (more fields, even though every one of them is itself a leaf value),
  `depth_staging` as a property value — expands multi-line.
- 2-space indent, trailing newline, `nodes` sorted by `id`, `edges` sorted by `(from, to)`.

## Not in this file

Canvas/layout positions (`tools/graph`'s canvas re-runs Dagre auto-layout on every load — never
persisted, so it can't pollute a diff), sessions, homework, activities, a sign-off appendix, or
persona *definitions*.
