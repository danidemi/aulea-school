== Before class

This item runs immediately after the gateway has already been deployed to GKE and confirmed
reachable (sequence 5, `PRQ-GKE-DEPLOY-GATEWAY`, and the sequence 6 checkpoint
`DR-DEPLOY-GATEWAY`). It also follows the route-model lecture-demo (`PRQ-GATEWAY-ROUTE-CONFIG`,
sequence 7) and the path-based-routing concept lesson (`PRQ-PATH-BASED-ROUTING`, sequence 8) —
`[stated]`, per the `PRQ-LEGACY-VS-NEW-ROUTING-IMPL -> PRQ-PATH-BASED-ROUTING` edge in DESIGN.
There is little fresh environment provisioning; this is mostly making sure the running gateway
from earlier in the session is still in a known-good state.

* Confirm: the gateway deployed in sequence 5 is still Running/Ready and reachable, exactly as
  checkpointed at sequence 6. `[stated]`.
* Decide and have ready: a small, concrete set of paths for the exercise — at minimum one
  `/legacy/**` path and one path per migrated microservice the room is using. CURRICULUM names
  only "a small set of paths" (`exercise_sheet` support material) without listing them —
  PLACEHOLDER: the exact path list and each backend's address (legacy system URI, each
  microservice's in-cluster address) are not in any store and must be supplied by the
  instructor/client before class.
* Have ready: the `exercise_sheet` support material ("Route rules exercise: given a small set of
  paths, write and deploy the split") and the `test_script` support material ("Script of sample
  requests to fire at the gateway to confirm the split"), both named on this CURRICULUM item.
  `[stated]`.
* Resolve beforehand (see instructional_decisions above): whether route rules are declared via
  Java DSL or YAML config for this team, since it changes how "deploy the updated route
  configuration" is actually done and how long it takes. `[inferred]`.
* Verify beforehand: apply the intended route split yourself against the deployed gateway and
  confirm each path resolves to the correct backend before the room attempts it, so an
  environment problem (a wrong backend address, an unreachable legacy system) is caught before
  it looks like a student error. `[inferred]`.

== What the lanes do

P-DEV (contributor)::
Writes/adjusts the concrete route rules for `/legacy/**` vs each migrated microservice.
`[stated]`, from the item's `lane_tasks`.

P-OPS (contributor)::
Deploys the updated route configuration and verifies traffic actually splits as intended.
`[stated]`, from the item's `lane_tasks`.

Both lanes are active contributors on this item — there is no observer or skip role here.

== Common failure points to watch for

* P-DEV lane: a `/legacy/**`-style predicate written broadly enough that it also matches a
  migrated path, so the migrated path is silently swallowed by the legacy rule instead of
  reaching its microservice. `[inferred]`.
* P-DEV lane: route ordering — if a general or catch-all route is declared before the specific
  legacy/migrated rules, it can intercept requests meant for the more specific routes.
  `[inferred]`.
* P-OPS lane: deploying the updated configuration but not confirming the gateway actually picked
  it up (stale routes served from a not-yet-reloaded or not-yet-restarted instance).
  `[inferred]`.
* P-OPS lane: firing test requests from inside the exercise sheet's script without checking each
  one lands on the intended backend — treating "the gateway responded" as sufficient, when the
  actual check is "the correct backend responded." `[inferred]`.

== What done correctly looks like

Applying the sample requests from the `test_script` support material against the deployed
gateway, a request to a `/legacy/**` path is answered by the legacy system, and a request to
each migrated path is answered by the corresponding microservice — confirmed by the instructor
from admin/log access (e.g. which backend's logs show the request landing, or a response body/
header identifying the backend), not merely by the gateway returning any HTTP response.
`[inferred]`, scoped per the instructional_decisions entry above.

== How the following checkpoint will be verified

The next item, `DR-STRANGLER-ROUTING` (sequence 10), is the checkpoint for this work. Its

to a migrated path is routed to the corresponding microservice, verified live against the
deployed gateway by both participants." `[stated]`. Its lane split mirrors this item's: P-DEV
confirms the route rules match the intended split, P-OPS fires test requests at the live gateway
and confirms the observed split. `[stated]`. Unlike several other checkpoints in this
