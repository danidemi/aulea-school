* Have the gateway from PRQ-GATEWAY-ROUTE-CONFIG (session 1, sequence 7) already running and
  reachable, with two routes already declared and deployed: one route whose predicate matches
  +/legacy/**+ and directs to the legacy system, and one route whose predicate matches at least
  one other path and directs to a migrated microservice. [inferred] Neither store gives the exact
  path names or target addresses used in this deployment; see the placeholder in the live

* Have a terminal or client (browser, curl, or an HTTP client tool) ready to send a request to

== Live sequence

. *Show* the diagram briefly. *Say:* "This is the shape we are about to make happen live: one
  path pattern, +/legacy/**+, goes to the legacy system. Every other configured path goes to a
  migrated microservice. The route model itself — predicates and filters — was covered a moment
  ago; what's new here is using a path predicate specifically to decide which system gets the
  request."
. *Run* a request against a path that matches +/legacy/**+ [invented framing, placeholder]:

*Say:* "Watch where this lands. The predicate matched +/legacy/**+, so the gateway sends it to
the legacy system, not to any of the new microservices."
. *Point at* the response (or, if visible, the target system's own log line showing it received
  the request). *Say:* "That's the legacy system answering — the path predicate decided that on
  its own."
. *Run* a second request against a path that does not match +/legacy/**+ [invented framing,
  placeholder]:
+
[source,placeholder]
----
<< exact request (URL, method, tool) against the deployed gateway's non-/legacy/** route — no
   store gives this deployment's actual host, port, or path; confirm with the client before

*Say:* "Same gateway, same moment in time, different path. This one lands on the migrated
microservice instead — same predicate mechanism, opposite outcome."
. *Point at* the diagram again, then at both responses side by side. *Say:* "This is the whole
  idea: one path pattern is the switch. Nothing in the request itself was rewritten to make this
  happen — the path alone decided the destination. Making this split solid and verified for our
  own real paths is exactly what we do next."

== What to watch for

* [inferred] Participants with an Ops background have just spent sequences 3 and 5 working with
  Kubernetes Ingress and GKE service exposure. They may expect this path split to be an
  Ingress-level or load-balancer-level rule. Say explicitly that this is the gateway
  application's own route configuration, evaluated inside the gateway process after a request has
  already reached it — not a Kubernetes or network-layer rule.
* Watch the room during the pause between sending each request and the response appearing. This
  is a 10-minute item with two request/response round-trips; if either pause runs long, narrate
  what should be happening ("the predicate is being matched right now") rather than standing
  silently.
* After the second request lands on the migrated microservice, check that the room connects it
  back to the strangler-fig framing from PRQ-STRANGLER-FIG-PATTERN (sequence 1): this predicate
  is the mechanism that lets the legacy system and the new microservices coexist behind one
  address during the migration window.

== Fallback

* If either request in the live sequence does not return the expected response, do not debug the
  route configuration live — that risks pre-empting or contradicting sequence 9's hands-on
  correction of the same rules. Switch to a pre-captured transcript of a known-good run of both
  requests. [invented framing, placeholder] No such transcript exists yet; capture one (terminal
  output or screenshot for both the +/legacy/**+ request and the non-+/legacy/**+ request) during
  a dry run before this item is first taught, and save it at a path the teacher can name here.
  Narrate it as "this is what a working split looks like."
* If the whole gateway or either target system is unreachable, skip the live requests entirely
  and stay on the diagram already open from Before class. Narrate the same two-request story
  against the diagram: point at the +/legacy/**+ branch, say what would happen, point at the
  other branch, say what would happen there.
* Whichever fallback is used, close on the same line as the live version: "the path alone decides
  the destination" — so the transition into sequence 9's hands-on implementation still lands on
  the right idea even if nothing ran live.
